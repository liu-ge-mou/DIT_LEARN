# 按场景执行接力

## 首次配置

先区分项目内容、接力机制、仓库连接三件事。用户只要求接力时，不替他创建业务应用；仓库不可访问时仍可完成本地机制。

检查现有 remote 和用户已给信息。一个明确且符合用户意图的远程可直接沿用；多个目标或身份不明时只确认目标。读取和同步私有仓库使用本机既有认证；不要输出凭据、令牌或带认证信息的 URL。不要为了接力自动改变仓库可见性或创建新的外部资源。

接力机制的最小实现：

- 确定唯一的当前进度入口，沿用现有 `docs/progress.md`、任务系统或状态文件。
- 在现有 `AGENTS.md` 中合并简短的读取/更新约定，保留原有规则。检查子目录覆盖规则，不能假设根文件一定生效。
- 保留项目现有的环境声明、锁文件、启动和验证命令；将缺失的复现信息补到已有说明。
- 依据实际内容补充忽略规则；明确大型资料、依赖缓存和外部数据如何到达另一台设备。

可合并到现有规则的最小约定（替换为真实文件路径）：

> 开始任务时读取项目说明和当前进度入口，并核对当前分支、提交与工作区。结束或切换设备前更新当前任务、进度、验证结果和下一步。进度记录使用项目相对路径，凭据只记录配置方式。

不复制整个机器的 Codex 配置目录来达成同步。项目需要的技能、工具和连接应有各自的来源和安装说明。对需要核实的 Codex 版本特性，查看当前官方文档或目标端能力，不推断聊天、后台进程或插件会自动随 Git 同步。

## 换机继续

1. 从实际状态开始：读取规则和状态入口，检查当前工作区以及记录中的分支和版本。确认操作对象是用户指定的项目，尤其避免在错误克隆中拉取或覆盖资料。
2. 本地干净且目标明确时获取所选远程的最新引用。`fetch` 只更新引用，不能替代读取差异。分支只落后且可快进时，按项目惯例显式快进；已分歧时不自动重置或强制拉取。
3. 工作区有改动时先检查归属和需要保留的内容；不为方便拉取自动清理、stash 或切换分支。现有 merge/rebase 等操作应先弄清状态再继续。
4. 用已有锁文件和实际运行时恢复依赖；不要把另一台设备的虚拟环境或构建产物当成可移植环境。
5. 按[环境参考](portability.md)检查当前任务需要的外部资料、技能和本机配置。执行适当的启动、构建、内容渲染或测试验证。验证失败时区分环境缺失与项目自身错误。
6. 简短说明恢复到的任务和版本，然后直接完成用户要求继续的工作。仅当缺失信息真正阻塞后续时提问。

## 离机交接

使用[接力记录](handoff-record.md)的字段更新当前状态入口。已有任务系统时链接具体任务，不另建平行待办。

若用户授权保存到 Git：先看 diff 和暂存区，明确哪些文件属于当前任务，再暂存和提交。不要使用全量添加将本机配置、未审阅资料或其他任务卷入交接；存在其他已暂存改动时不要直接把整个暂存区提交。

创建交接提交前的状态文档记录 `base_commit`，即此次提交的父版本或此前确认的基准。提交之后的最终 hash 在交接回复或已有任务系统中报告，避免为了把文档写成“自身提交的 hash”反复 amend。文档里的同步状态以 Git 实测为准，不为声称已推送再制造一个未推送的文档提交。

若用户授权推送：使用已确认的 remote 和明确分支，检查推送结果，并将远程分支对应 hash 与交接提交比较。失败时保留本地工作，报告可操作原因；相同认证/网络失败不无限重试，不用 force push 解决分歧。

用户未授权远程写入、处于离线状态或目标未知时，交付本地记录和准确待办；如需要可传输包，只打包经过选择的项目内容，注明接收端仍待验收。

## 接力验收

按实际可用的设备和资源选择能执行的层级：

| 已执行的检查 | 可以声称 | 尚不能声称 |
|---|---|---|
| 文件与进度已保存 | 本地已保存 | 对端可获得这些内容 |
| 远程引用已确认包含交接提交，必要资料传输路径明确 | 远端交接已确认 | 目标电脑环境可运行 |
| 临时干净检出恢复成功 | 同机干净检出已验证 | 另一台设备已验证 |
| 目标端版本、资料与最小验证均通过 | 该设备上的该任务已恢复 | 所有任务和所有设备均已验证 |

首次配置可用临时干净检出验证当前范围；不要为文档修改强制跑全套业务测试。保存运行命令、结果和版本依据，明确没有执行的检查。
