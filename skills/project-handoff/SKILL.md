# 跨设备项目接力

让接手设备能够恢复正确的文件、任务上下文和工作环境，并清楚知道下一步。围绕项目建立可携带的事实记录；聊天历史是否可用，不应成为唯一恢复条件。

## 先判断场景

从对话和项目中识别当前操作，不必逐项询问：

| 场景 | 要交付的结果 | 按需读取 |
|---|---|---|
| 首次配置 | 沿用现有规范的最小接力机制 | [接力流程](references/workflows.md)，必要时读取环境参考 |
| 换机继续 | 核对版本、恢复环境、明确下一步并继续原任务 | [接力流程](references/workflows.md) |
| 离机交接 | 保存实际进度，确认可传输内容和剩余缺口 | [接力记录](references/handoff-record.md) |
| 无法接续或多人并行 | 找出缺文件、缺环境、记录过期或版本分歧的原因 | [环境与特殊场景](references/portability.md) |

首次配置通常适合 Git 远程仓库；已有其他同步方式时先评估并保留用户选择。Windows + GitHub 是常见组合，不是前提。文档、数据分析、LaTeX、代码项目分别沿用自己的验证方法。

## 检查事实，再选择动作

1. 读取适用的 `AGENTS.md`、项目说明、现有进度与环境配置。沿用现有状态文件；只有确实缺失时才增加 `docs/STATUS.md` 等文件，避免多个互相矛盾的进度源。
2. 检查实际目录、分支、改动、upstream、远程与工作树。可使用本技能的只读助手（Python 3.9+、Git）：

   ```powershell
   python "<skill-directory>/scripts/inspect_project.py" --path "<project-directory>"
   ```

   使用已检测可用的解释器和实际路径。助手不访问网络，不读取文件内容或远程 URL；`ahead/behind` 仅比较本地缓存。退出码 0 表示检查执行成功，不表示可接力。没有 Python 时用原生 Git 和文件检查完成同样的判断，不必为此安装运行时。
3. 检查任务需要的源码、资料、技能、外部数据和工具是否可携带。凭据分别在每台设备配置；记录变量名和获取途径，不记录密钥值。
4. 只询问影响下一步的缺失信息，例如多个远程中应使用哪个。缺少仓库标识时继续完成本地设计、记录与诊断。沿用已有授权，不反复要求批准已明确的操作。

## 按规模调整

- **轻量单人接力**：一份状态记录 + `AGENTS.md` 中的读取/更新约定 + 已有环境说明即可；不强制生成脚本、数据库、容器或 CI。
- **已有工程**：补齐薄弱环节，保留目录结构、锁文件、团队约定和已有自动化。
- **频繁接力或环境复杂**：依据实际重复操作补充启动/交接脚本、数据清单或干净检出验证。
- **多设备同时写入**：任务分支和显式整合；工作树只提供单机隔离。共享状态文档不是分布式锁。

## 保存与恢复的边界

首次配置、诊断、换机继续本身不意味着发布改动。用户明确要求提交/推送交接时，结合已有授权、已确认仓库和文件范围执行；不把“可以用 GitHub”解释为允许创建公开仓库、发布、合并或重写历史。

存在本地改动、冲突或分支分歧时，先保全并检查，选择符合项目约定的处理方式。只提交本次交接应包含的明确文件，检查暂存区，保留其他工作。GitHub CLI、插件都可选，采用当前可用且已授权的接口。

进度文档是恢复线索，文件和 Git 是版本证据。核对记录对应的版本后，执行当前任务所需的最小验证；用户说“继续”时，恢复完成后继续原任务，不停在汇报状态。

## 完成时说清楚

报告任务、实际分支/提交、资料和环境缺口、下一步，以及已验证的接力阶段：**本地已保存 / 远端已确认 / 目标设备已验证**。有本地修改时明确它们尚不属于哪个提交；只有推送成功不能证明另一台电脑已恢复。无法访问另一台设备时给出准确验收步骤，不声称已完成目标端验证。

验证助手本身可运行：`python "<skill-directory>/scripts/test_inspect_project.py"`；它仅在临时目录创建本地测试仓库，不访问 GitHub。
